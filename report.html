The GNU pair, zoomed: glibc vs musl

Every warm run for the two GNU-grep containers on a 0–1 s axis; the heavy tick marks each container's mean. Alpine ships the newer grep (3.12 vs 3.8) yet trails by ~20% — glibc's SIMD-tuned string routines beat musl's on bulk scanning.

Cold-cache penalty

First query after dropping the VM page cache, as a multiple of the container's warm mean. The GNU containers are I/O-bound when cold (~3 s to pull 5 GB off disk) and CPU-light once cached. BusyBox barely notices the cache — the CPU is the bottleneck either way.

Is grep even the fastest way?

Same lookup, five strategies, both GNU-grep containers (warm cache, find phase only — decryption adds ~2 ms to any of them; every strategy returned identical match counts). Pure Python holds its own, parallelism is the big lever, and an index makes scanning look silly.

The pure-Python scanner (mmap + bytes.find, CPython's C-level two-way search) matches GNU grep with no subprocess and no packages — and it runs at the same speed on musl as glibc, so it turns a stock Alpine image's ~36 s BusyBox query into ~0.69 s with nothing installed. Splitting the five files across five worker processes cuts that to ~0.16 s. Ripgrep's spread is packaging, not musl: Debian bookworm ships rg 13.0.0, Alpine ships rg 15.1.0 with newer SIMD paths. The index (one row per UUID in SQLite mapping to packed file/byte-offset pairs, then seek + readline per match) took a one-time 5.6 s scan to build, weighs 126 MB, and answers in ~1 ms — and unlike every scanning strategy it stays ~1 ms as the dataset grows.

Findings

  • Stock Alpine is a performance trap for this workload. BusyBox grep is a minimal naive matcher — no Boyer–Moore skipping, no vectorized memchr, small read chunks. At ~36 s per lookup, the Python app spends its life waiting on the subprocess.
  • The fix is one line: apk add grep. GNU grep shadows the BusyBox applet and recovers ~97% of the gap with zero change to the Python code — the same subprocess argv simply resolves to a different binary.
  • The remaining ~20% is libc, not grep version. Debian's older GNU grep 3.8 on glibc (0.73 s) outruns Alpine's newer 3.12 on musl (0.87 s). If lookup latency matters most, a glibc base wins; the hardening applied here (non-root, no setuid, dropped capabilities, read-only rootfs) cost nothing measurable.
  • grep isn't the ceiling. A pure-Python mmap scan parallelized across files runs the same lookup in 0.16 s (~4–5× faster than GNU grep, libc-independent), and a one-time UUID→offset index answers in ~1 ms. If lookups are a real access pattern rather than ad-hoc forensics, index — every scanning strategy pays O(dataset) per query.
  • Encryption is a rounding error. AES-256-GCM decryption of ~732 matched lines takes 1.6–2.7 ms — under 0.3% of even the fastest query. The design question for this pipeline is entirely "which grep", not "what does crypto cost".

Methodology

The application under test times its two phases separately:

subprocess.run(["grep", "-F", "-h", uuid, *files])   # phase 1: find
AESGCM(key).decrypt(nonce, ciphertext, None)         # phase 2: per matched line
ContainerBase imagegrep binaryNotes
alpine-busyboxpython:3.12-alpine/bin/busyboxstock image, BusyBox applet
debian-hardenedpython:3.12-slim-bookworm/usr/bin/grepnon-root user, setuid/setgid bits stripped
alpine-gnugreppython:3.12-alpine/bin/grepstock image + apk add grep

Dataset: 5 × 1.01 GB JSONL files (12.5M lines) in a named Docker volume, so I/O stays inside the Linux VM rather than crossing the macOS bind-mount boundary. Each line carries an id UUID shared by 500–1000 lines (interleaved with ~250 other active UUIDs) and a msg of base64(nonce ‖ AES-256-GCM ciphertext). UUIDs contain dashes, which cannot occur in base64, so a fixed-string match can only hit the id field. All three containers ran with identical flags (--cap-drop ALL --security-opt no-new-privileges --read-only) and searched the same seeded set of 5 UUIDs: one cold pass immediately after dropping the VM page cache, then two measured warm repetitions.

Reproducibility: this page shows the second full pipeline run. The first run (fresh dataset, separate cache drops) agreed within a few hundredths of a second on every GNU-grep and Python number; BusyBox was ~4% slower there (38.1 s warm mean, i.e. 52× vs this run's 50×).

Caveat: absolute numbers come from Docker's aarch64 VM on a Mac (8 vCPU / 8 GB); treat the relative rankings as the durable result.
